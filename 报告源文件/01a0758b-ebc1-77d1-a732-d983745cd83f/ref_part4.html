05 / 端侧部署链路

从浮点权重到 BPU 定点模型

六个环节，每一步都对应一次真实的工程决策

关键参数速查

量化架构march: bayes-e——RDK X5 的 BPU 架构，换板卡必须同步修改
输入规格input_name: "x1; x2"，input_shape: "1x3x256x256; 1x3x256x256"，双输入参数一律用分号分隔写同样多份
量化方式calibration_type: default + preprocess_on: False——用真实数据校准，且预处理已在生成校准集时完成
编译策略compile_mode: latency，optimize_level: O2，core_num: 1——面向低延迟单帧推理
最容易踩的坑：多输入模型的参数必须写成同样多份（如 cal_data_type: "float32; float32"）。 只写一份会直接报 Wrong cal_data_type num given，工具在参数数量上不做默认补齐。

06 / 工程深度

一次真实的量化故障排查

这段过程最能体现"算法与硬件协同"的工程判断力，建议在答辩中重点讲

现象

第一次量化采用 calibration_type: skip（不提供真实数据，由工具用随机数据校准）。 工具链报告 Convert to runtime bin file successfully，产物大小 2,820,223 字节，看起来一切正常。 但拷到板子上跑真实影像，输出的变化像素占比是 0.0000——模型"瞎了"。

根因

量化需要知道每一层激活值的真实分布范围，才能把 float32 映射到 int8。 用随机数据算出的分布完全不对，量化后数值坍塌，输出几乎恒定为一个常数。 skip 只适合验证模型结构能否通过检查，绝不能用于真实推理。

定位方法：先"分锅"，再动手

第 1 步
写浮点自检脚本
绕过量化，直接用 .pth 在 CPU 上跑同一张图，看模型本身能否检出变化
|
第 2 步
看浮点结果
预测变化占比 0.1885，真实标签 0.2012 —— 几乎一致
|
第 3 步
得出结论
模型与预处理完全正确，问题 100% 出在 skip 量化
为什么这一步关键：如果不做浮点自检，很容易误判成"模型不行 / 预处理写错了"， 进而在错误的方向上反复重训。先用浮点结果把责任划分清楚，才能精准定位到量化环节。

修复与验证

步骤做法与结果
生成真实校准集从训练集抽 60 组 A/B，按训练同款预处理生成 x1 / x2 两套 float32 裸数据，每组 786,432 字节
改用 default 校准calibration_type: default，preprocess_on: False，校准目录用分号分隔双输入
重新量化产物由 2,820,223 字节变为 3,279,032 字节——模型不再坍塌，权重信息更有效
板端复测全量测试集 F1 达到 0.8648，量化后精度与浮点模型基本持平
可复用的经验：①量化必须用真实数据校准；②精度异常时先在浮点侧验证，别急着重训； ③浮点自检、ONNX 导出、校准数据生成、板端推理四处预处理必须完全一致，任一处不一致结果都会崩。
